# Django Admin: роли и разрешения

## Роли пользователей

Роль задаётся в поле `role` модели `User` и назначается через Django-админку суперпользователем.

| Значение `role` | Название | Описание |
|---|---|---|
| *(пусто)* | — | Обычный пользователь, нет доступа в админку |
| `admin` | Администратор | Полный доступ ко всем разделам |
| `hall_manager` | Менеджер зала | Только бронирования столов и записи на мероприятия |
| `content_manager` | Контент-менеджер | Меню, мероприятия, новости, устройства FCM |

Суперпользователь (`is_superuser=True`) имеет полный доступ независимо от `role`.

## Матрица разрешений

| Раздел | Администратор | Менеджер зала | Контент-менеджер |
|---|---|---|---|
| `User` (пользователи) | ✅ полный | ❌ | ❌ |
| `TableBooking` (брони) | ✅ полный | 👁️ просмотр + полное редактирование (без создания и удаления) | ❌ |
| `EventReservation` (записи на события) | ✅ полный | 👁️ просмотр + изменение | ❌ |
| `Event` (мероприятия) | ✅ полный | ❌ | ✅ полный |
| `News` (новости) | ✅ полный | ❌ | ✅ полный |
| `Category`, `Tag`, `Allergen`, `Dish` | ✅ полный | ❌ | ✅ полный |
| `UserDevice` (FCM-устройства) | 👁️ просмотр + 🗑️ удаление (добавление/изменение недоступны из-за бага — см. «Важные нюансы») | ❌ | 👁️ просмотр + 🗑️ удаление (то же, что и у администратора) |
| `RestaurantInfo` (настройки ресторана) | ✅ изменение (добавление/удаление заблокированы — синглтон) | ❌ | ✅ изменение |
| `InteriorPhoto` (фото интерьера) | ✅ полный | ❌ | ✅ полный |

| `PushCampaign` (push-рассылки) | ✅ полный (удаление — только суперпользователь) | ❌ | ✅ (без удаления) |

## Как назначить роль

1. Войти в Django-админку как суперпользователь.
2. Перейти в раздел **Users → Пользователи**.
3. Открыть нужного пользователя.
4. Убедиться, что `is_staff = True` (без этого пользователь не попадёт в админку).
5. Выбрать нужную роль в поле **Роль**.

## Техническая реализация

Разрешения проверяются через переопределение методов `has_view_permission`, `has_add_permission`, `has_change_permission`, `has_delete_permission` в каждом `ModelAdmin`.

Файлы:
- `apps/users/admin.py` — `AdminOnlyMixin` + `UserAdmin`
- `apps/bookings/admin.py` — `TableBookingAdmin` (`hall_manager` + `admin`)
- `apps/events/admin.py` — `EventAdmin`, `NewsAdmin` (content), `EventReservationAdmin` (hall)
- `apps/menu/admin.py` — `ContentManagerMixin` + все модели меню
- `apps/notifications/admin.py` — `UserDeviceAdmin` (content + admin), `PushCampaignAdmin` (content + admin, удаление — только суперпользователь)
- `apps/core/admin.py` — `RestaurantInfoAdmin` (content + admin), `InteriorPhotoAdmin` (content + admin), `AppVersionAdmin` (только admin)

## Важные нюансы

- Если у пользователя выставлен `is_staff=True`, но `role` пустой, он может войти в интерфейс, но не увидит ни одного раздела.
- Менеджер зала **не может** создавать или удалять брони, но может отредактировать **любое** поле существующей брони (имя гостя, телефон, дату, время, зону, комментарий, статус и т.д.) через Django-админку — никакого ограничения «только статус» в коде нет. Отдельного Staff API для броней (`/api/v1/bookings/staff/...`) в проекте не существует — управление ведётся исключительно через Django-админку.
- Контент-менеджер **не видит** пользователей и их данные — только контентные разделы.
- `UserDeviceAdmin` (`apps/notifications/admin.py`) определяет `has_add_permission`/`has_change_permission` дважды: сначала — с проверкой роли, затем — безусловно `return False`. Python использует **последнее** определение метода в классе, поэтому добавление и изменение `UserDevice` в админке недоступно вообще никому (включая суперпользователя). Реально работают только просмотр и удаление (`has_delete_permission` определён один раз и разрешает их admin/content_manager).
