## 1. Mobizon «на будущее»

**Цель:** оценить Mobizon (казахстанский SMS-шлюз) как альтернативу/дополнение к текущему провайдеру для масштабирования.

**Текущее состояние:** Mobizon нигде не используется (0 совпадений по репозиторию). Реальный провайдер — `backend/apps/users/tasks.py::send_sms_task` шлёт POST с полями `login/psw/phones/mes` — это **конкретно smsc.ru-контракт**, а не абстрактный. `SMS_PROVIDER_URL/LOGIN/PASSWORD` (`backend/config/settings/base.py:207-209`) — просто конфиг-строки, формат запроса не абстрагируют. OTP-логика — `backend/apps/users/services.py::SMSService` (4 цифры, Redis `otp_{phone}`, TTL 180с).

**Находка:** Mobizon API использует другой контракт (`recipient/text/apiKey` вместо `login/psw/phones/mes`) — не drop-in замена через смену только URL. Плюс с 2026 действует платная регистрация именного отправителя по операторам (~10 рабочих дней) — это бизнес/бюджетный вопрос.

**Технический хвост (можно сделать сейчас):**
- Не патчить `send_sms_task` спекулятивно веткой `if provider == 'mobizon'`.
- Если решение «подключаем» будет принято — заводить отдельный тонкий клиент-класс по образцу `backend/apps/remarked/client.py` (реальный контракт другой).
- Задел: можно добавить в `base.py` заготовку `SMS_API_KEY` (env, default='') рядом с `SMS_LOGIN/SMS_PASSWORD`, ничего не включая.

**Тесты:** не нужны, пока нет реального клиента. Когда появится — по образцу `SendSmsTaskTest`/`SMSServiceTest` в `backend/apps/users/tests.py`.

**Результат:** короткая заметка «подходит/не подходит + чего не хватает» — не блокер для остальных задач.

**Решено пользователем (2026-08-15):** зафиксировать вывод и отложить — не тратить время на углублённое исследование тарифов/сроков сейчас. Задача считается закрытой в рамках этой итерации (вывод уже зафиксирован выше); интеграция начнётся только если и когда появится отдельное бизнес-решение.

## 6. Вход по новому ТЗ (фазированно — документ прямо запрещает полную реализацию без ответов на 6 вопросов)

### Фаза A — код-исследование (выполнено и подтверждено)

Проверено `backend/apps/remarked/client.py` и `openapi.json` (подтверждено прямым чтением обоих файлов):
- `RemarkedMobileClient` сейчас реализует только `get_info_by_phone(phone)` и `create_or_update(user, ...)`. Метода поиска «по номеру участника» нет.
- **Но:** ответ `CustomerResponse.data` в `openapi.json` **документированно** содержит поле `cards` — `"Список номеров карт"`, `type: array` (проверено прямым запросом к схеме). Это отличается от `card_shortcode`, который использует `apply_guest_data_to_user()` для `loyalty_card_url` — `card_shortcode` в openapi.json **действительно не документирован** (подтверждено — его нет в списке полей `CustomerResponse.data`), что соответствует комментарию в коде «найдено эмпирически».
- **Вывод:** технически пара «телефон + номер участника» **проверяема уже сегодняшним API**, без доработок со стороны Remarked — можно дёрнуть существующий `get_info_by_phone(phone)` и сравнить введённое число с `guest['cards']`. Это отвечает на техническую часть открытого вопроса №1 из ТЗ.
- **Остаётся проверить эмпирически (не выдумывая):** совпадает ли `cards[0]` с числом, которое реальный гость видит на своей карте в Apple Wallet — это разные системы, гарантии соответствия нет. Требуется 10-минутная проверка на реальном тестовом госте.
